## 4.1 GCSバケットの分割設計

テーブル単位や連携元システム単位でバケットを分割するのは、バケット数上限やIAM/Terraform管理の複雑化を招くためアンチパターンである。「連携用バケット（DMZ）＋ レイクハウス本体バケット」の2バケット構成（またはメダリオンレイヤー別バケット構成）とし、データ連携元やテーブルはバケット内のディレクトリ（プレフィックス）で分割する。

- **`gs://{env}-data-landing`（連携用バケット / DMZ）**
  - **役割**: 外部システムやSaaSから生のCSV / JSON / Parquetを受け取る緩衝地帯。
  - **権限**: 外部システムにはこのバケットの特定プレフィックス（例：`gs://prod-data-landing/system_a/*`）への書き込み権限（IAM Condition）のみを付与し、レイクハウス本体には触れさせない。
  - **ライフサイクル**: GCSのオブジェクトライフサイクル管理（OLM）を有効化し、配置から30日〜90日経過したファイルを自動削除またはArchiveへ移行する。
- **`gs://{env}-lakehouse-main`（レイクハウス本体バケット）**
  - **役割**: データ基盤のパイプラインがLandingバケットからデータをPullして変換し、OTF（`bronze/`、`silver/`、`gold/`）として一元管理する領域。
  - **ライフサイクル**: GCS側の自動削除設定（OLM）はオフにする。有効なParquetファイルが消えてテーブルが破損するのを防ぐためであり、容量回収は必ずOTF側の `VACUUM` や `expire_snapshots` で行う。

## 4.2 GCSのオブジェクト数上限とボトルネックへの対策

- **オブジェクト数と容量の上限**: GCSの1バケット内に保存できるオブジェクト（ファイル）数や総容量に上限は存在しない。上限やレート制限が問題になるのは「プロジェクトあたりのバケット作成数」であるため、テーブル単位でのバケット分割は避け、少数のバケット内に全テーブルを集約する設計とする。
- **3つのボトルネックとOTFの優位性**:
  - **秒間リクエスト数（QPS）とホットスポット**: GCSはプレフィックス（ディレクトリ名）の辞書順で裏側のサーバーを自動シャーディングする（初期上限：書き込み 1,000 req/秒、読み込み 5,000 req/秒）。さらに高並列な処理が必要な場合は、バケット作成時に「階層型名前空間（Hierarchical Namespace: HNS）」を有効化することで初期QPS上限を最大8倍に引き上げられる。
  - **`LIST` 操作の排除**: 従来のHive形式データレイクはクエリ時に遅い `storage.objects.list` APIを呼び出す必要があった。一方、OTFはメタデータ（Manifest / JSON）内に有効なParquetファイルのフルパスを記録しているため、`LIST` 操作を行わず直接 `GET` リクエストを発行でき、数千万ファイル規模でも初動が劣化しない。
  - **小ファイルによるAPI課金増**: 小さなファイルが増えるとClass Bオペレーション課金とオープン処理のオーバーヘッドがかさむため、定期的な `Compaction（OPTIMIZE）` と `VACUUM` によって総オブジェクト数を適正化する。

## 4.3 GCSストレージクラスの選定指針

- **レイクハウス本体バケット（`gs://{env}-lakehouse-main`）**
  - **原則として「Standard（標準）」を選択する**: Nearline（最低30日）、Coldline（90日）、Archive（365日）を手動設定すると、OTFの `Compaction` や `VACUUM` で数日〜数週間以内に古いParquetファイルが物理削除された際、最低保管期間の残り日数分の「早期削除ペナルティ」が課金される。また、クエリ時の「データ取り出し料金（Retrieval Fee）」や高いオペレーション単価によりコストが増える。
  - **長期コールドデータがある場合の「Autoclass」活用**: 1年以上前の古いパーティションが大量にあり滅多に参照されない場合は、バケット単位で「Autoclass（自動クラス変換）」を有効化する。Autoclassはアクセス頻度に応じて自動でクラスを昇降格させ、かつ「早期削除ペナルティ」と「データ取り出し料金」が免除されるため、OTFの `VACUUM` と干渉しない。
- **連携用バケット（`gs://{env}-data-landing`）**
  - 初期配置は Standard とし、オブジェクトライフサイクル管理（OLM）で「30日〜90日後に自動削除」または「30日後にColdline / Archiveへ自動遷移し、1年後に自動削除」を設定する。

## 4.4 Apache Icebergにおけるスキャン量削減（プルーニングとクラスタリング）

BigQueryネイティブテーブルと同様に、Icebergでもパーティションとクラスタリングによってクエリスキャン量を削減できる。

1. **3段階のプルーニング（読み込みスキップ）**
   - **① パーティション・プルーニング（Manifest List層）**: 条件に合致しないパーティションのManifest File自体をスキップする。
   - **② ファイル・プルーニング / Data Skipping（Manifest File層）**: 各Parquetファイルのカラム統計情報（Min / Max / Null数）を参照し、条件に合致しないParquetファイルの読み込みをスキップする（BigQueryネイティブのクラスタリングと同等の効果）。
   - **③ 行グループ＆カラム・プルーニング（Parquetファイル内部）**: `SELECT` された列のみを読み込み、Parquet内のRow Group統計情報で不要ブロックをスキップする。
2. **Hidden Partitioning（隠れパーティション）の優位性**
   - BigQueryネイティブと異なり、タイムスタンプ列に対して `days(created_at)` や `months(created_at)` のような変換ルールをメタデータ側で保持する。クエリ作成者が関数を意識せず `WHERE created_at >= '2026-11-14 10:00:00'` と書くだけで自動的にパーティションが絞り込まれ、誤ってフルスキャンしてしまう事故を防げる。
3. **クラスタリングの設定方法**
   - **BigLake Managed Tables（BigQuery書き込み）**: DDLやdbtで `CLUSTER BY customer_id, created_at` を指定すれば、BigQueryが裏側で自動ソートと自動コンパクションを実行する。
   - **外部エンジン（Databricks / Spark書き込み）**: 書き込み時に `WRITE ORDERED BY` や `Z-Order` / `Liquid Clustering` を適用しておくことで、各ParquetのMin/Max範囲が狭まり、BigQueryからの参照時にもManifest統計情報によるファイルスキップが機能する。

## 4.5 レイクハウス本体バケットのIAM権限設計

- **基本原則（人間にはGCSの直接権限を渡さない）**
  - 開発者やデータアナリストを含む人間のユーザーには、レイクハウス本体バケット（`gs://prod-lakehouse-main`）の書き込み権限だけでなく、直接読み取り権限（`roles/storage.objectViewer`）も付与しない。
  - **理由**: 手動でのファイル操作によるOTFの論理破損を防ぐためである。あわせて、カタログ層（BigLake / Unity Catalog）で設定した動的データマスキング（PII保護）や行フィルタをバイパスしてPython等からParquetを直接読み取られる情報漏洩リスクを塞ぐ目的もある。
- **ロール別の権限割り当て**
  - **BigLake Connection / Unity Catalog のサービスアカウント**: `roles/storage.objectUser` または `roles/storage.objectAdmin`（ストレージの読み書きを行う唯一のアカウント）。
  - **開発者・アナリスト（人間）**: GCS権限はゼロとする。BigQueryのデータセット閲覧権限（`roles/bigquery.dataViewer`）やUnity Catalogの `SELECT` 権限のみを付与し、必ずカタログ経由でアクセスさせる。開発検証は別バケット（`gs://dev-lakehouse-main`）に紐づく開発用データセット経由で行わせる。
  - **バケット設定**: バケット作成時に「均一なバケットレベルのアクセス（Uniform bucket-level access）」を有効化し、オブジェクト単位のACLを無効化する。

## 4.6 単一バケット集約における保護・復旧・特権オーバーライド対策

レイクハウス本体バケット（`gs://{env}-lakehouse-main`）に全テーブルを集約する設計では、人為・論理事故の影響範囲が1箇所に集中するリスクに備え、「3層の防御・復旧策」と「オーナー/編集者権限のオーバーライド対策」を講じる。

### 単一バケット保護の3層防御（Prevent / Recover / Isolate）

1. **消せないようにする防御策（Prevent）**
   - Terraform等のIaCコードにおいて、バケットリソースに `lifecycle { prevent_destroy = true }` を設定する。
   - `storage.buckets.delete` 権限を持つロールを日常運用アカウントから排除し、BigLake Connectionやパイプライン実行用SAにはオブジェクト操作権限のみを付与する。
2. **消されても戻せる復旧策（Recover）**
   - **GCS Soft Delete（ソフトデリート）の活用**: バケット削除やオブジェクト削除が発生した場合でも、保持期間（デフォルト7日、最大365日）内であれば復元できる。OTFの日常的な `VACUUM` と共存させるため、保持期間は短め（例：7日）に設定してストレージ膨張を抑える。
   - **別プロジェクトへの定期バックアップ / レプリケーション**: 本番バケットとは別のGCPプロジェクトにバックアップ用バケットを設け、Storage Transfer Service等で定期的に複製を保持する。
3. **被害を広げない構造・権限分離（Isolate）**
   - 本番環境（`prod`）と開発環境（`dev`）でバケットおよびGCPプロジェクトを分離し、さらにレイヤー（Bronze / Silver / Gold）やジョブ単位で書き込み用サービスアカウントを分ける。

### オーナー・編集者権限のオーバーライド（IAM拒否ポリシーと構造分離）

通常のIAM（許可ポリシー）は「権限の足し算」であり、`roles/owner` や `roles/editor` の権限を削ることはできない。これには以下の2つのアプローチで対処する。

1. **IAM拒否ポリシー（IAM Deny Policy）の適用**
   - 評価順序において許可ポリシーより優先される「IAM拒否ポリシー」を組織・フォルダ・プロジェクト単位で設定する。
   - `deniedPrincipals`（拒否対象）、`deniedPermissions`（例：`storage.googleapis.com/objects.create`、`objects.delete`、`buckets.delete`）、`exceptionPrincipals`（BigLake Connection用SAや緊急復旧用ブレイクグラスアカウントの除外指定）、`denialConditions`（リソースタグによるバケット条件分岐）を指定する。これにより、プロジェクトオーナーや編集者であっても手動でのファイル書き込み・削除をブロックできる。
   - **注意点**: バケット単体には直接アタッチできないため、同一プロジェクト内に他バケットがある場合はリソースタグ条件が必要となる。また、拒否ポリシー自体の管理権限（`iam.googleapis.com/denyPolicies.*`）まで誤って拒否するとロックアウトされるため、検証環境での事前テストが必須となる。
2. **構造的なガードレール設計（推奨）**
   - **データ基盤専用プロジェクトへの分離**: 開発者やアプリチームがオーナー・編集者を持つプロジェクトとは別の「データ基盤専用プロジェクト」に `lakehouse-main` バケットを分離する。
   - **人間の常時特権ロールの廃止**: その専用プロジェクトでは人間のアカウントに常時の `roles/owner` や `roles/editor` を付与せず閲覧ロール等に留め、強い権限が必要な作業時のみPAM（Privileged Access Manager）等で一時昇格させる。
