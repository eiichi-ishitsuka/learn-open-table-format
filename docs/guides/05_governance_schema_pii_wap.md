## 5.1 スキーマの変化（Schema Drift）への耐性

- 上流システムの予告なきカラム追加や型変更に対し、`Schema Merge（自動追従）` や `Rescued Data Column（_rescued_dataカラムへの一時退避）` を活用することで、深夜・早朝の取り込みパイプラインをエラーで止めずにデータを保護できる。dbtモデル側の修正は後から非同期で行えばよい。
- カラムのリネームや削除も、過去数年分のParquetファイルを再構築（バックフィル）することなくメタデータ操作だけで完了する。

## 5.2 個人情報（PII）のマスキングと削除要求（GDPR等）への対応

1. **遡及マスク・物理削除の高速化（`UPDATE` ＋ Deletion Vectors ＋ `VACUUM`）**
   - 退会ユーザーの個人情報を過去数年分のソースデータから消去・マスクする際、従来の生ファイル群では全ファイルの再展開・再作成が必要だった。
   - OTFではソーステーブルに対して直接 `UPDATE bronze.users SET email = '***' WHERE user_id = 123` を実行できる。Deletion Vectors（削除ベクトル）によって元のParquetファイルを書き直さずに小さな差分ファイルを生成するだけで、数秒で完了する。
   - 法的な抹消が必要な場合は、続けて `VACUUM` / `expire_snapshots` を実行して過去スナップショットから物理消去する。
2. **EL取り込み時のPII分離（PII Vaultパターン）**
   - 取り込み時にPIIカラムをハッシュ化するか、権限分離された別バケットのOTFテーブル（PII Vault）へ切り出し、通常のBronzeテーブルにはPIIを含めない設計を組める。
3. **クエリ時の動的マスキング（Dynamic Data Masking）の注意点**
   - OTF自体の仕様にはアクセス制御が含まれないため、動的マスキングはカタログ層（BigQueryのポリシータグ、Unity CatalogのColumn Mask）で行う。マルチエンジン環境で設定の二重管理や抜け漏れを防ぐため、生PIIを含むBronzeへの直接アクセスは基盤のサービスアカウントのみに限定し、マスク済みのSilver/Goldを公開する設計とする。

## 5.3 データのGit管理（ブランチ・タグ）とWAP（Write-Audit-Publish）パターン

Apache Icebergのテーブル内ブランチ・タグ機能を用いることで、本番データに異常値を混入させないパイプライン運用が実現できる。

1. **Write（隔離ブランチへの書き込み）**: 本番（`main`）ではなく、作成した `audit_branch` に対してバッチデータを書き込む。この時点では本番ユーザーからは見えない。
2. **Audit（品質検査）**: `VERSION AS OF 'audit_branch'` に対してデータ品質テスト（NULLチェックや異常値検知）を実行する。異常があればブランチを破棄するだけで、本番テーブルには影響しない。
3. **Publish（Fast-Forwardマージ）**: テスト合格後、`fast_forward` プロシージャで `main` のポインタを `audit_branch` のスナップショットへ切り替える。データのコピーなしで0.1秒で本番反映が完了する。
4. **Tag（タグによる長期保護）**: 月末決算確定時点や機械学習モデルの学習データセット時点のスナップショットに `TAG` を付与し、通常の `VACUUM` 対象から除外してゼロコピーで長期保存する。
