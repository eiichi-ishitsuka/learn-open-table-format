## 1.1 エグゼクティブサマリー

オープンテーブルフォーマット（Open Table Format: OTF）は、Google Cloud Storage（GCS）やAmazon S3などのオブジェクトストレージ上にあるカラムナファイル群（主にParquet）の上に「メタデータ層」と「カタログ層」を設ける技術である。これにより、データウェアハウス（DWH）と同等のACIDトランザクション、スキーマ進化、タイムトラベルを実現する。

本ガイドでは、Apache Icebergを軸としたデータレイクハウスを導入するにあたり、既存DWH運用の課題整理からOTFの基本構造、フォーマット選定ロードマップ、GCSインフラ・セキュリティ設計、データガバナンスまでを整理する。あわせて、Apache Airflow 2系・dbtを用いた移行・運用手順を定義する。

## 1.2 従来のデータレイク（Hive形式等）の課題

従来のデータレイク（Apache Hive形式など）では、ディレクトリ単位でファイルを管理していたため、以下の課題が存在した。

- **更新・削除の非効率性**: 1行だけデータを更新・削除したい場合でも、パーティション全体のファイルを書き直す必要がある。
- **トランザクションの欠如**: 書き込み中に別のクエリが実行されると、不整合なデータ（書きかけのデータ）を読み込んでしまう。処理失敗時のロールバックもできない。
- **メタデータと統計情報の不足**: ディレクトリ一覧の走査（`LIST` 操作）に時間がかかり、ファイル単位のスキップが難しい。

## 1.3 通常のBigQueryネイティブテーブルへのロード（従来型DWH運用）の課題

BigQueryのネイティブストレージに直接データをロード（`bq load` や Data Transfer Service 等）する従来のアプローチは、単一DWH内で完結する場合はシンプルで高速である。一方、マルチエンジン環境や大規模・高頻度なデータ基盤運用では、以下の6つの課題が生じる。

- **マルチエンジン連携時のデータの二重管理・再移動**: データがBigQuery内部ストレージに閉じ込められるため、DatabricksやSpark、Pythonワーカー等の外部エンジンから同じデータを利用する際に、Storage Read APIによる大規模通信やGCSへの再エクスポート（`EXPORT DATA`）と取り込みジョブが必要になる。これにより、パイプラインの二重管理やタイムラグ、ストレージとネットワークの二重課金が発生する。
- **スキーマ変化（Schema Drift）による取り込みジョブの停止**: 上流システムが予告なしにカラムを追加・リネーム・型変更した場合、`bq load` 等のロードジョブがスキーマ不一致エラーで停止しやすい。OTFのようなIDベースのカラム管理（リネーム・削除のメタデータ反映）や救済カラム（`_rescued_data` への異常データ退避）がないため、カラム削除や型変更のたびにテーブル全体の再作成（バックフィル）やアラート対応が発生する。
- **タイムトラベル期間の7日間ハードリミット**: BigQueryネイティブテーブルのタイムトラベル機能には最大7日間という上限がある。8日以上前に混入したデータ不整合の調査やロールバックを行うには、スナップショットやバックアップテーブルを別途設計・定期実行する必要があり、運用とコストが増える。
- **高頻度CDC（差分更新・削除）とPII遡及マスクのコンピュートコスト**: 業務DBからの高頻度なCDC反映や、退会ユーザーのPII（個人情報）を過去数年分の履歴から遡及して `UPDATE` / `DELETE` / `MERGE` する際、BigQueryのコンピュートリソース（スロットまたはスキャン量課金）を大きく消費する。
- **パーティション定義変更時のテーブル再作成**: 運用途中で「月次パーティションから日次パーティションへ変更したい」といった場合、BigQueryネイティブテーブルでは既存テーブルのまま定義を切り替えられない。全データの再書き込み（マイグレーション）が必要となる。
- **本番テーブルへの直接ロードによるデータ混入リスク（ブランチ機能の欠如）**: ネイティブテーブルにはテーブル単体でのブランチ機能（WAP: Write-Audit-Publish）がない。ステージングテーブルを別途作ってデータを二重に書き込む（I/Oとコストの倍増）か、本番テーブルへ直接ロードして異常データ混入時に事後ロールバックするリスクを許容する必要がある。
